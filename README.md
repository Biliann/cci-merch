# CCI — Портал мерча для дистрибьюторов

Рабочий full-stack MVP: React 19 + TypeScript, Vinext (совместимые с Next.js App Router страницы и API), Cloudflare Worker, D1 (управляемая SQLite), Drizzle schema/migrations. PostgreSQL в эту версию не включён. Логотип `public/cci-logo.png` — оригинальный файл пользователя без изменений. Все товары, цены, остатки, имена и компании в демо являются тестовыми; изображения — локальные SVG-иллюстрации, не фотографии официального ассортимента.

## Возможности

- Вход email/пароль, серверные сессии в HttpOnly SameSite cookie, выход с отзывом сессии. Регистрации нет.
- Два демо-дистрибьютора, четыре региона, по 8 отдельных региональных SKU (32 SKU всего).
- Размерные варианты, остатки на вариант и товар, поиск, категории, выбор количества.
- Корзина одного региона с пересчётом, удалением и изменением количества. Черновик хранится отдельно для каждого пользователя в localStorage на устройстве; заказы и история — в D1.
- Отдельное окно подтверждения. Заказ создаётся только после его подтверждения.
- Сервер пересчитывает цены из БД. Атомарный D1 batch сохраняет заказ, позиции, outbox и списывает остатки. CHECK constraints не дают уйти в минус при конкурентных заказах. Повторный запрос checkout с тем же ключом возвращает существующий заказ.
- Неизменяемые снимки названий, артикулов и цен в заказах; история доступна только владельцу.
- Уведомления через Resend. Без API key письмо сохраняется в outbox со статусом `preview`, без попытки реальной отправки. Ошибка email-провайдера не отменяет сохранённый заказ; в демо есть повторная отправка.
- Случайная 256-битная ссылка поставщика; в заказе хранится SHA-256 токена. GET только показывает заказ, POST после явного нажатия подтверждает получение. Повторное подтверждение безопасно.
- «Мои заказы» автоматически обновляются каждые 12 секунд; есть ручное обновление.
- Кабинет, адаптивная сетка 4/3/2 колонки, доступные с клавиатуры модальные окна.

## Локальный запуск

Нужен Node.js >= 22.13 и pnpm 11 (версия зафиксирована в package.json).

```sh
pnpm install --frozen-lockfile
pnpm build
node scripts/setup-db.mjs
pnpm dev
```

Откройте URL из терминала (обычно http://localhost:5173). Локальная D1 хранится в `.wrangler/state` и переживает перезапуски. `setup-db.mjs` предназначен для **первой установки** на пустую БД: не запускайте существующие SQL-миграции повторно. При дальнейших изменениях создавайте новые миграции через `pnpm db:generate` и применяйте только новые файлы.

Для переменных окружения создайте `.dev.vars` по `.env.example`. Без этого файла демо работает с email preview. Не коммитьте `.dev.vars`, секреты и runtime-данные.

Предпросмотр production Worker локально после `pnpm build`: `pnpm start`.

## Автоматический выбор магазина

После входа на новом устройстве портал запрашивает разрешение браузера на геолокацию и открывает каталог ближайшего регионального центра: Алматы (Юг), Астана (Север), Атырау (Запад), Усть-Каменогорск (Восток). Это предварительное правило по расстоянию, а не утверждённые зоны доставки CCI. Когда появятся границы обслуживания, обновите `lib/region-location.ts`.

Координаты обрабатываются только в браузере и не сохраняются и не отправляются на сервер. В localStorage сохраняется только выбранный регион отдельно для каждого аккаунта. При повторном входе открывается сохранённый магазин, а при незавершённом заказе приоритет имеет регион корзины. Кнопка «Определить регион» позволяет повторить определение, а список регионов остаётся доступен для ручного выбора. Ручной выбор отменяет ожидающий результат геолокации.

При отказе, тайм-ауте, отсутствии геолокации или местоположении за пределами Казахстана портал предлагает ручной выбор. Контур страны упрощён, поэтому вблизи границы может потребоваться ручной выбор. Для браузерной геолокации нужен HTTPS или localhost. При встраивании в iframe контейнер также должен разрешать `geolocation` через Permissions Policy и атрибут `allow`.

Проверка определения регионов: `node tests/location.mjs`.

## Демо-аккаунты

| Email | Пароль |
|---|---|
| distributor1@demo.com | demo123 |
| distributor2@demo.com | demo123 |

Демо-пользователи, поставщики и каталог создаются атомарно при первом API-запросе, если `DEMO_MODE` не равен `false`. Начальные данные описаны в `app/catalogue.ts`; существующая БД не перезаписывается при перезапусках. Чтобы менять существующий каталог, редактируйте записи `products`/`variants` в БД; изменение seed-файла само по себе их не изменит.

## Полная демонстрация

1. Войдите первым аккаунтом или нажмите «Войти как дистрибьютор 1» в блоке «Демо-доступ», разрешите геолокацию или выберите «Юг» вручную.
2. Откройте футболку, выберите L и количество; добавьте в заказ.
3. Добавьте второй SKU, откройте «Заказ», измените количество/удалите позицию.
4. Нажмите «Оформить заказ». «Отмена» не создаёт заказ.
5. Подтвердите заказ. Проверьте номер, сумму и исходный статус.
6. Перейдите в «Мои заказы» → детали → «Открыть письмо».
7. Нажмите «Проверить подтверждение поставщика»; в новой вкладке подтвердите получение.
8. Вернитесь к заказу и нажмите «Обновить статус» либо дождитесь автообновления.
9. Перезагрузите страницу и откройте историю: заказ сохранён.
10. Выйдите, войдите вторым аккаунтом: первый заказ ему недоступен.

## Email

Настройте runtime secrets `RESEND_API_KEY`, `EMAIL_FROM` (адрес на подтверждённом домене Resend), четыре `SUPPLIER_*_EMAIL` и при необходимости `APP_URL` (внешний HTTPS origin). Формат запроса соответствует [официальному Resend API](https://resend.com/docs/api-reference/emails/send-email); используется `Idempotency-Key` для повторов. Никаких реальных писем при разработке не отправлялось: API key не предоставлен.

- `EMAIL_PREVIEW=true` + демо-режим показывают письмо и защищённую ссылку **только владельцу заказа**.
- `EMAIL_PREVIEW=false` или `DEMO_MODE=false` скрывают демо-просмотр письма.
- Без `APP_URL` ссылка строится из origin входящего запроса.
- Поставщики по умолчанию имеют зарезервированные адреса `@example.com`. Замените их перед подключением настоящей отправки.
- Статус заказа «Отправлен поставщику» обозначает этап бизнес-процесса; фактическая отправка email отдельно хранится в `outbox.status`. Без ключа интерфейс явно сообщает о режиме предпросмотра. Ответ email API подтверждает принятие провайдером, а не доставку во входящие; delivery webhooks не реализованы.

## Развёртывание и доступ

Этот проект публикуется через Sites с D1 binding `DB`. Манифест `.openai/hosting.json`, SQL и Drizzle metadata входят в исходники; Sites применяет production-миграции. Локальная и production БД независимы.

Режим доступа настраивается в Sites и сохраняется при обновлении приложения. Внутри портала данные дистрибьютора защищены входом по email/паролю. Для пилота проверьте согласованные компанией настройки доступа дистрибьюторов и поставщиков.

Перед реальным использованием:

1. Загрузите согласованные SKU, фото, остатки и адреса поставщиков.
2. Создайте реальные учётные записи, отключите демо через `DEMO_MODE=false` (также блокирует вход уже существующих `demo-*` пользователей). Демо seed при этом не запускается. Сначала создайте реальный каталог/аккаунты.
3. Уберите демонстрационные заказы из production БД, если они есть; локальные тесты production данные не меняют.
4. Подключите Resend и настройте внешний origin/доступ поставщиков.
5. Проверьте backup/restore и принятые компанией требования безопасности. Password reset, административный портал, автоматический email retry worker и аудит безопасности не входят в MVP.

`node scripts/provision-user.mjs` принимает JSON через stdin (`name`, `company`, `email`, `password`, `region`) и выдаёт SQL с PBKDF2-SHA256 хешем; пароль не выводится. Передавайте данные через безопасный локальный stdin, не аргументы shell, затем примените SQL к нужной БД через Wrangler или консоль D1. Скрипт требует пароль длиной от 12 символов. Публичного endpoint создания пользователей нет.

## Структура

- `app/page.tsx` — интерфейс портала, корзина, модальные окна, страницы истории/поставщика.
- `app/api/portal/route.ts` — API, авторизация, серверная валидация, seed, оформление, email, подтверждение.
- `app/catalogue.ts` — тестовый ассортимент и регионы.
- `app/globals.css` — адаптивный дизайн, состояния и доступность.
- `db/schema.ts`, `drizzle/` — схема и SQL-миграции.
- `public/` — оригинальный CCI logo и иллюстрации.
- `scripts/provision-user.mjs`, `scripts/setup-db.mjs` — ручное обслуживание.
- `tests/api.mjs` — 40 интеграционных проверка на изолированной D1.

## Проверки

```sh
pnpm exec tsc --noEmit
node tests/api.mjs
pnpm build
```

API-тесты выполняют реальные обработчики запросов на изолированной in-memory D1 через Miniflare; импорты environment привязываются к тестовой БД. Они не поднимают HTTP сервер, не используют production БД и не отправляют почту. Проверяются вход, выход, четыре региона, размеры/количества, расчёты, сохранение, идемпотентность, списание остатков, изоляция пользователей, email preview, защищённое подтверждение, обновление статуса и конкурентные заказы. Browser QA дополнительно проверяет настоящий Worker/Vinext путь.


## Русский и казахский языки

- Переключатель РУС / ҚАЗ есть на странице входа, в основном header и на странице поставщика. Предпочтение сохраняется в localStorage и отдельной несекретной cookie `cci_locale`; сессия авторизации независима от языка.
- `lib/translations.ts` — централизованный словарь казахских переводов; русский текст служит исходным ключом. Неизвестные пользовательские данные не изменяются.
- `app/i18n-provider.tsx` — React Context с локалью `ru | kk`, переключателем, `html.lang` и заголовком вкладки. Перевод выполняется при рендеринге, без подмены DOM.
- `lib/i18n.ts` — общие чистые функции для клиента и сервера: перевод, локаль запроса, суммы в тенге и даты по Asia/Almaty. Названия месяцев заданы явно, чтобы казахские даты работали и в браузерах с неполными ICU-данными.
- `lib/order-email.ts` — отдельный экранированный HTML-шаблон уведомления поставщика. Письмо создаётся в языке оформления заказа, сохраняется как снимок в outbox и при повторной отправке не меняется. Ссылка включает `lang=ru` или `lang=kk`. Старые письма сохраняют исходный язык.
- В БД и запросах остаются прежние канонические регионы, категории, статусы и SKU. Смена языка не меняет корзину, размеры, цены, остатки и идентификаторы. Миграция БД не требуется.
- В текущем демо переведены названия и описания всех 32 SKU. При ручном добавлении новых товаров добавляйте соответствующие переводы в словарь.
- Проверки охватывают локализованные ошибки, казахское письмо и ссылку поставщика, оформление с исходными SKU/ценами, статусы и полноту статических переводов.
